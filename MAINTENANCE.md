## 1. Repository Overview

This repository hosts the **formsflow.ai installation documentation** as a static site built with [Docusaurus v3](https://docusaurus.io/). The site is published to **GitHub Pages** and is publicly accessible at:

```
https://aot-technologies.github.io/forms-flow-installation-eks/
```

The documentation covers installation of formsflow.ai on:
- **Windows** (local/Docker)
- **Linux** (local/Docker)
- **Kubernetes / EKS** (AWS Elastic Kubernetes Service)

### Key Characteristics

| Property | Value |
|---|---|
| Framework | Docusaurus v3.5.2 |
| Hosting | GitHub Pages (via GitHub Actions) |
| Deployment trigger | Push to `main` branch |
| Source served | `chart-doc/build/` directory |
| Current versions | v7.3.0, v7.1.0, v7.0.0 |
| Active development ("Next") | `chart-doc/docs/` |

### ⚠️ Critical: The `build/` folder

Unlike most projects, the **`build/` directory is committed to Git**. This is intentional — the GitHub Actions workflow (`static.yml`) directly uploads `chart-doc/build/` to GitHub Pages without running a build step on the CI server. This means:

- You **must always rebuild locally** before committing and pushing.
- The `build/` folder in Git must always reflect the latest content.

## 4. How the Documentation Site Works

### Docusaurus Versioning Model

Docusaurus uses a **snapshot-based versioning system**:

```
docs/           → "Next" version (work-in-progress, not yet released)
versioned_docs/ → Frozen snapshots of past releases
```

- The **`docs/`** folder is always the bleeding-edge content. It is shown in the site as **"Next"** and is configured in `docusaurus.config.js` as:
  ```js
  current: { label: 'Next', path: 'next', badge: false }
  ```
- When you run `npm run docusaurus docs:version vX.Y.Z`, Docusaurus **copies** the entire `docs/` folder into `versioned_docs/version-vX.Y.Z/` and freezes it.
- Each version gets its own sidebar snapshot in `versioned_sidebars/`.
- The `versions.json` file lists all published versions in descending order.

### Deployment Flow

```
Local edits
    │
    ▼
npm run build (inside chart-doc/)
    │  Generates chart-doc/build/
    ▼
git add + git commit + git push (to main)
    │
    ▼
GitHub Actions (static.yml) triggers automatically
    │  Uploads chart-doc/build/ to GitHub Pages
    ▼
Site live at https://aot-technologies.github.io/forms-flow-installation-eks/
```

## 5. Updating Existing Documentation Content

### Updating the Current ("Next") Docs

Edit files directly inside `chart-doc/docs/`:

```
chart-doc/docs/windows.md        ← Windows installation guide
chart-doc/docs/linux.md          ← Linux installation guide
chart-doc/docs/intro.md          ← Kubernetes overview
chart-doc/docs/eks.md            ← AWS EKS guide
chart-doc/docs/tenant-creation.md ← Multi-tenancy guide
```

```bash
# 1. Make your edits
# 2. Preview locally
cd chart-doc
npm start

# 3. Build
npm run build

# 4. Commit everything (including the updated build/)
cd ..   # back to repo root
git add chart-doc/docs/
git add chart-doc/build/
git commit -m "docs: update windows installation guide for vX.Y.Z"
git push origin main
```

### Updating a Released Version

> ⚠️ **Only do this to correct errors/typos — do not add new features to old versions.**

Edit the file directly in the corresponding versioned folder:

```bash
# Example: Fix a typo in v7.3.0 linux guide
chart-doc/versioned_docs/version-v7.3.0/linux.md
```

Then rebuild and commit:

```bash
cd chart-doc
npm run build
cd ..
git add chart-doc/versioned_docs/version-v7.3.0/
git add chart-doc/build/
git commit -m "docs: fix typo in v7.3.0 linux guide"
git push origin main
```

### Adding a New Documentation Page

1. Create a new `.md` file in `chart-doc/docs/`:
   ```bash
   # Example: adding a docker-compose guide
   touch chart-doc/docs/docker.md
   ```

2. Add front matter at the top of the file:
   ```md
   ---
   id: docker
   title: Docker Compose Installation
   sidebar_position: 3
   ---
   ```

3. Register it in `chart-doc/sidebars.js` (see [Section 6](#6-sidebar--navigation-changes)).

4. Build and commit.

## 6. Sidebar & Navigation Changes

The sidebar is defined in `chart-doc/sidebars.js`. The current structure is:

```js
const sidebars = {
  tutorialSidebar: [
    'windows',
    'linux',
    {
      type: 'category',
      label: 'Kubernetes',
      items: ['intro', 'eks'],
      collapsed: true,
    },
  ],
};
```

### Adding a New Page to the Sidebar

```js
const sidebars = {
  tutorialSidebar: [
    'windows',
    'linux',
    'docker',          // ← Add your new page ID here
    {
      type: 'category',
      label: 'Kubernetes',
      items: ['intro', 'eks'],
      collapsed: true,
    },
  ],
};
```

> ⚠️ The value used in `sidebars.js` must match the `id` in your document's front matter, or the filename (without `.md`) if no `id` is set.

### Versioned Sidebars

When you create a new version, `versioned_sidebars/sidebars-vX.Y.Z.json` is auto-generated. **Do not manually edit these files** unless you are fixing a bug — they should mirror the `sidebars.js` state at release time.

## 7. Creating a New Version

Official Documentation: [https://docusaurus.io/docs/versioning](https://docusaurus.io/docs/versioning)

This is the process for releasing a new formsflow.ai version's documentation. Follow these steps exactly.

### Step 1: Update the "Next" docs

Make sure all content in `chart-doc/docs/` is complete and accurate for the new version. Review every `.md` file.

### Step 2: Update the version badge in `README.md`

In the root `README.md`, update the version badge:

```md
<!-- Find this line and change the version number -->
<img src="https://img.shields.io/badge/release-v8.0.0-blue"/>
```

### Step 3: Run the Docusaurus version command

```bash
cd chart-doc
npm run docusaurus docs:version v8.0.0
```

> Replace `v8.0.0` with the actual version. **Always prefix with `v`** (e.g., `v7.4.0`, not `7.4.0`).

This command will automatically:
- Copy `docs/` → `versioned_docs/version-v8.0.0/`
- Copy `sidebars.js` → `versioned_sidebars/sidebars-v8.0.0.json`
- Prepend `"v8.0.0"` to `versions.json`

### Step 4: Verify `versions.json`

```bash
cat versions.json
```

Expected (newest first):
```json
[
  "v8.0.0",
  "v7.3.0",
  "v7.1.0",
  "v7.0.0"
]
```

### Step 5: Preview locally

```bash
npm start
```

Check that:
- The new version `v8.0.0` appears in the version dropdown
- The "Next" docs still work
- All links and images resolve correctly
- The sidebar for the new version is correct

### Step 6: Build

```bash
npm run build
```

Fix any errors before proceeding. Common errors:
- Broken internal links (`onBrokenLinks: 'throw'` is set — any dead link will fail the build)
- Missing images referenced in markdown

### Step 7: Commit and push everything

```bash
cd ..   # back to repo root

# Stage all changed files
git add chart-doc/docs/
git add chart-doc/versioned_docs/version-v8.0.0/
git add chart-doc/versioned_sidebars/sidebars-v8.0.0.json
git add chart-doc/versions.json
git add chart-doc/build/
git add README.md

# Commit
git commit -m "release: add documentation for v8.0.0"

# Push
git push origin main
```

> ⚠️ **Do NOT forget to stage `chart-doc/build/`**. If you forget, the live site will be out of date but there will be no error — it will silently serve stale content.

### Step 8: Verify the live site

After the GitHub Actions workflow completes (usually 1–2 minutes), visit:
```
https://aot-technologies.github.io/forms-flow-installation-eks/
```
Check the version dropdown and confirm the new version is live.

## 8. Build Process

### Running the Build

All build commands must be run from `chart-doc/`:

```bash
cd chart-doc

# Development server (hot-reload, no build output)
npm start

# Production build (generates chart-doc/build/)
npm run build

# Serve the production build locally to verify before pushing
npm run serve

# Clear Docusaurus cache (do this if you see stale content during dev)
npm run clear
```

### What `npm run build` Does

1. Reads `docusaurus.config.js` for site configuration
2. Reads `versions.json` to determine which versioned docs to include
3. Processes all `.md` files in `docs/` and `versioned_docs/`
4. Validates all internal links (throws on broken links)
5. Outputs the complete static site to `chart-doc/build/`

### Build Output Structure

```
chart-doc/build/
├── index.html              ← Site entry (redirects to latest version)
├── 404.html
├── sitemap.xml
├── .nojekyll               ← Tells GitHub Pages NOT to process with Jekyll
├── docs/                   ← "Next" docs at /docs/next/
│   └── next/
├── assets/                 ← Bundled JS/CSS
└── img/                    ← Static images
```

## 9. Deployment to GitHub Pages

### Automatic Deployment (Standard Process)

Deployment is **fully automated** via GitHub Actions. The workflow is defined in [`.github/workflows/static.yml`](.github/workflows/static.yml).

**Trigger:** Any push to the `main` branch  
**Action:** Uploads `chart-doc/build/` to GitHub Pages  
**Result:** Live within 1–3 minutes

```yaml
# What the workflow does (simplified):
- Checkout repository
- Upload chart-doc/build/ as a GitHub Pages artifact
- Deploy to GitHub Pages
```

### No Build Step in CI

> ⚠️ **Critical:** The CI workflow does **NOT** run `npm run build`. It directly uploads whatever is in `chart-doc/build/` at the time of the push. **You must always build locally and commit the `build/` folder.**

### Manual Trigger

You can also trigger deployment manually from the GitHub Actions tab without making any code changes:

1. Go to the repository on GitHub
2. Click **Actions** → **Deploy static content to Pages**
3. Click **Run workflow** → Select `main` → Click **Run workflow**

This re-deploys whatever is currently in `chart-doc/build/` on the `main` branch.

### Checking Deployment Status

1. Go to **Actions** tab in GitHub
2. Look for the **"Deploy static content to Pages"** workflow
3. Green checkmark = deployed successfully
4. Red X = failed — click to view logs

## 10. Critical Gotchas & Things to Watch Out For

### 🔴 Always Commit the `build/` Folder

This is the most important rule. The GitHub Actions deployment workflow reads `chart-doc/build/` **directly from Git**. If you edit docs but don't run a build and commit the output, the live site will NOT be updated.

**Checklist before every push:**
- [ ] Ran `npm run build` inside `chart-doc/`
- [ ] `git add chart-doc/build/` was included in the commit
- [ ] Build completed without errors

### 🔴 Broken Links Will Fail the Build

`docusaurus.config.js` has `onBrokenLinks: 'throw'`. Any internal link that points to a non-existent page will **abort the build** with an error. Before committing, always run a full `npm run build` to catch broken links.

### 🔴 Version Command Creates a Snapshot — It Cannot Be Undone Cleanly

Running `npm run docusaurus docs:version vX.Y.Z` creates files and updates `versions.json`. While you technically can manually delete the generated folder and revert `versions.json`, it is messy and error-prone. **Make sure `docs/` is final before running the version command.**

### 🟡 `node_modules/` Is NOT Committed

The `chart-doc/.gitignore` correctly excludes `node_modules/`. When cloning the repo fresh, always run `npm install` inside `chart-doc/` before doing any work.

### 🟡 The `docs/` Folder Is Always "Next"

Content in `chart-doc/docs/` is displayed as the **"Next"** (unreleased) version on the live site. It is visible to users who select "Next" from the version dropdown. Only create a version snapshot when the content is truly ready for a release.

### 🟡 `baseUrl` Is Set to `/forms-flow-installation-eks`

In `docusaurus.config.js`:
```js
baseUrl: '/forms-flow-installation-eks',
```
All internal links must be relative or account for this base path. Do not hardcode absolute paths starting with `/` unless you include the base path.

### 🟡 Version Naming Convention

Always use the `v` prefix (lowercase): `v7.3.0`, `v8.0.0`. The `versions.json` and folder names (`versioned_docs/version-v7.3.0/`) all follow this convention. Inconsistent naming will break the version dropdown.

### 🟡 Images in Versioned Docs

If a versioned doc references an image (e.g., `redash.png`), that image must exist in the **same versioned folder** (`versioned_docs/version-vX.Y.Z/`) or in `static/`. Images in `docs/` are NOT automatically copied to versioned folders — you must copy them manually before running the version command if they are referenced by relative paths.

### 🟡 The `.docusaurus/` Cache

The `.docusaurus/` folder is a build cache and is git-ignored. If you see unexpected behavior during local development (stale pages, incorrect routing), run:
```bash
cd chart-doc
npm run clear
npm start
```

## 12. Troubleshooting

### Build fails with "broken link" error

```
Error: Docusaurus found broken links!
```

**Cause:** An internal link in a `.md` file points to a page or anchor that does not exist.  
**Fix:** Search the docs for the broken link referenced in the error message and correct or remove it.

---

### Site looks stale after pushing

**Cause:** The `chart-doc/build/` folder was not updated before pushing.  
**Fix:**
```bash
cd chart-doc
npm run build
cd ..
git add chart-doc/build/
git commit -m "chore: rebuild static site"
git push origin main
```

---

### GitHub Actions deployment fails

1. Go to **Actions** tab → Click the failed run → View logs
2. Common causes:
   - Permissions issue (rare — check repository Settings → Pages → Source is set to "GitHub Actions")
   - Branch protection rules preventing the workflow

---

### `npm start` fails with "Cannot find module" error

**Cause:** `node_modules/` is missing (fresh clone or was deleted).  
**Fix:**
```bash
cd chart-doc
npm install
npm start
```

---

### Version dropdown shows incorrect order

**Cause:** `versions.json` is not in descending order (newest first).  
**Fix:** Manually edit `chart-doc/versions.json` to put the newest version at the top:
```json
[
  "v8.0.0",
  "v7.3.0",
  "v7.1.0",
  "v7.0.0"
]
```
Then rebuild and commit.

---

### Images not showing up in a versioned page

**Cause:** Image file was placed in `docs/` but not copied to the versioned folder when the snapshot was taken.  
**Fix:** Manually copy the image file to the appropriate `versioned_docs/version-vX.Y.Z/` folder, then rebuild.
